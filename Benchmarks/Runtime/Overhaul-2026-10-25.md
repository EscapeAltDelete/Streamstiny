# Playback information, settings and emote verification

## Bitrate: source and lifetime corrected

The old monitor sampled `MediaPlayerTrack.bitRate`. In the pinned player,
`FFmpegAssetTrack` initializes this from `codecpar.bit_rate`, then overwrites it
with FFmpeg's `variant_bitrate` metadata where present. Opening a fixed HLS media
playlist often leaves the former zero; opening a master can supply declared
variant bandwidth, which is not video-only encoded bitrate. The old UI also put
the value in a video overlay instead of the playback information list.

The existing bitrate path now uses the active HLS representation's metadata and
labels its meaning accurately: **Advertised average bitrate** when a validated
AVERAGE-BANDWIDTH exists, otherwise **Advertised peak bitrate** from BANDWIDTH.
These can include audio and container overhead. They are neither measured
video-only bitrate nor network throughput. The monitor never invents a value or
subtracts guessed audio bandwidth. Audio-only or ambiguous representations with
insufficient metadata show unavailable. Twitch backup substitution also shows
unavailable rather than displaying primary-rendition metadata for different media.

Fixed selections work without a populated decoder bitrate. Automatic selection
matches the actual video dimensions/framerate and available variant metadata;
ambiguous same-size variants remain unavailable. HLS source renditions can match
their advertised bandwidth against the decoder's variant metadata. Quality and
source changes cancel stale work and clear stale values.

There is one monitor, driven by the existing player tick, with no additional
timer, network probe, decoder or media download. It collects metadata only while
the information view is open, at most once per second. It computes a new result
off the main actor only when its value-type input changes. Closing the view,
disabling Show Bitrate, switching or stopping playback cancels pending work.
Unchanged values do not repeatedly publish UI state. The permanent overlay was
removed. The information list also includes available viewer counts, active
resolution, quality, framerate and buffer duration.

Actual live iOS Simulator acceptance showed AngelThump at 1920×1080/60 fps with
**Advertised peak bitrate — 6.00 Mbps** in the information list. Screenshot/OCR
checks verified presence and removal, not merely formatter output.
The final confirmed-live provider run also verified Twitch at 8.04 Mbps and
Kick at 9.00 Mbps. Both passed two fixed-quality selections followed by return
to automatic selection, with the information row populated after each change.
All three provider tests passed with zero failures and zero skips.

## Emotes: verified result and unresolved device report

Current first-party metadata defines ARRIVE, BlackGuyLaptop, Classic, HUH and
COKEJAW, all without subscription restrictions. All five serve animated AVIF,
including URLs ending in GIF. The canonical metadata lookup, case-sensitive
token parser, shared loader, format normalization and WebKit rendering remain in
place. No alternate provider, four-name dictionary, second cache or replacement
renderer was added.

The v0.0.19 alpha-container normalization remains necessary: original ARRIVE,
Classic and HUH fail Apple decoding, whereas normalized bodies decode all
81/51/94 frames. The new COKEJAW diagnosis found the same defect: zero original
frames decoded versus all 62 after the existing generic normalization.
BlackGuyLaptop already decoded correctly without modification.
The original report and measurements are in
[the preceding investigation](Reliability-2026-10-25.md).

The exact **iOS 17.0** simulator produced eight distinct rendered frames for
**each of all five** through the existing application renderer. iOS 17.5 also
passed the complete six-test suite and all 347 catalog decodes; iOS 18.5 passed
the corresponding baseline checks. This disproves the initial hypothesis that
the current implementation necessarily fails merely because it runs on iOS 17.

The updated regression test additionally exercises cold and warm caches and
ordinary-user messages decoded through ChatProtocol, without privileged-user
fixtures. Listening, pepeW and PepoPunch remain existing regression checks and
were reported working by the user.

**The remaining physical-device failure was not reproduced.** There is no basis
to claim a new root cause or a new production emote fix in this follow-up.
The installed release version and whether the picker also fails were requested
to distinguish an older installation, token/metadata failure and image failure.
No physical iPad 8 or iPhone 12 mini was available. Simulator results do not
prove that the user's observed device problem is resolved.

## AngelThump delivery and recovery

Public first-party application resources confirmed the v3 streams API. A real,
unprotected live channel (`yodime`) was resolved using the application's existing
public viewer grant and Vigor HLS endpoint. Its master advertised a Source
rendition at 6 Mbps and delivered media through an AngelThump edge.

Seven successive media playlist samples showed a six-segment sliding window,
two-second segments, advancing MEDIA-SEQUENCE, PROGRAM-DATE-TIME and EXT-X-MAP.
The downloaded media was fMP4: styp, two sidx boxes, one moof and one mdat.
The samples exposed no PREFETCH, TWITCH-PREFETCH, PART, PART-INF, SERVER-CONTROL,
PRELOAD-HINT or ENDLIST. One full fragment and short segments do not establish
progressive early-media publication. This sample does not prove that every
AngelThump stream will always have identical capabilities.

The optional AngelThump low-latency setting is **off by default**. It reuses the
same HLSOptions/FFmpeg reader, starting two completed segments from the end rather
than FFmpeg's default three. It also reuses the existing short analysis setting.
It does not add prefetch expansion, a playlist gateway, future URL prediction,
a segment scheduler, or a second buffering/recovery system. Existing catch-up,
target-buffer, audio and hardware-decode behavior remain.

Four alternating Linux FFmpeg live probes completed successfully with five
segment requests each. Their first decoded frame times were:

| Start index | First decoded frame | Age relative to selected segment's program date |
| --- | ---: | ---: |
| −3 | 2.59 s | 7.32 s |
| −2 | 4.58 s | 9.62 s |
| −2 | 3.43 s | 7.86 s |
| −3 | 3.09 s | 10.66 s |

These variable network samples **do not establish an end-to-end improvement**.
Program-date age is not glass-to-glass latency, and the CLI is not the iOS player.
No startup, CPU, battery or physical-device latency improvement is claimed.
The toggle reduces the configured complete-segment safety margin; users can
leave it off for the prior behavior. Raw probe data is in
[the measurement summary](overhaul-2026-10-25.json).

Two concrete recovery defects were corrected within the existing controller:

- The AngelThump resolver converted non-array JSON into an empty stream list,
  incorrectly classifying malformed HTTP-200 error data as offline. It now
  validates the array and live record; malformed data remains recoverable.
  A valid empty provider response still means offline.
- KSPlayer can call its finish delegate with no error through `sourceDidFailed`
  without first updating `playbackState`. The wrapper now records completion
  directly from that callback and clears it when preparing replacement media.
  The existing bounded recovery controller consumes this event. This avoids
  stopping the ticking task while leaving the controller unaware of failure.

Decoder completion is still not authoritative broadcast termination. Existing
1/2/4-second bounded retries, source refresh, quality preservation, cancellation,
network restoration and validated direct-HLS ENDLIST handling remain. No second
retry manager was introduced. The user's original physical interruption has not
been captured; these are verified source-path defects, not a claim to have
reproduced that exact live failure chain.

## Settings organization and compatibility

General contains landscape layout. Player groups quality, catch-up, provider
latency/ad options and stream-information visibility. Chat groups appearance,
messages, emotes, interaction, links/language and authenticated website settings.
Notifications contains the existing whisper/mention preferences and permission
handling. Accounts retains the existing sign-in/out controls. No empty Advanced
category or unsupported options were invented.

All **36 existing AppStorage keys and defaults in SettingsView are preserved**;
the one additional preference is `angelthumpLowLatency=false`. Existing values
therefore need no storage migration or reset. Positive emote-control labels bind
to the original inverted keys. Native Forms, Sections, NavigationStack, Dynamic
Type controls and accessibility identifiers are retained. The existing
UserDefaults/AppStorage store remains authoritative; no additional settings
store or global observer was added. Chat preferences invalidate rendering when
leaving the page so changes apply even before another message arrives. Website
sync and account storage remain intact.

## Verification boundaries

The optimized ARM64 Release build, IPA validation, compiled Swift regression
executable and 19 Python tooling tests pass. Coverage includes zero/known bitrate,
fixed/automatic selection, malformed AngelThump responses, low-latency provider
isolation, and the existing Twitch/Kick/YouTube regressions. The complete native
iOS 18.5 suite passed seven tests with zero failures, including the five-emote
cold/warm checks and live bitrate plus injected completion/recovery. The later
menu test also verifies that closing it stops work with Show Bitrate still enabled,
and that recovery preserves fixed quality with AngelThump low latency enabled.

The initial live Twitch/Kick test channels were offline and were explicitly
skipped, not counted as verified playback. A subsequent run used confirmed-live
channels (`lirik` and `westcol`) and passed both quality-switch tests. The Catalyst player harness could not
build because KSPlayer declares Catalyst 13 while its pinned FFmpegKit dependency
requires 14; player acceptance therefore uses iOS Simulator with the production
dependency patches. The existing Catalyst chat-only harness remains supported.

There is no physical-device Instruments result, reliable glass-to-glass latency
measurement, GPU/energy profile or complete long-session failure matrix. No
application-wide CPU/RSS improvement is claimed from metadata/UI changes alone.
The prior chat measurements remain in the preceding report; this follow-up does
not change the message rendering algorithm.
