# Chat UX and efficiency audit — 26 October 2026

## Implementation

- A native 44-point floating button uses the renderer's existing follow state.
  Only state transitions cross the bridge. It sits 12 points inside the chat's
  safe area, supports VoiceOver and Reduce Motion, and fades in/out. Tapping
  follows the moving newest-message target for a finite 250 ms animation.
  User gestures cancel it; incoming messages preserve the older reading position.
  No new polling, observer, dependency, renderer or scroll-state owner was added.
- Native WebKit testing exposed an existing automatic-follow defect: requesting
  `scrollHeight` instead of the maximum scroll offset produced transient
  overscroll of an entire viewport. Both automatic following and the button now
  use `scrollHeight - clientHeight`. A pending acknowledgement preserves intent
  across asynchronous WebKit scrolling until its scroll event confirms arrival
  or the user intervenes. A synchronous DOM read is not a native-scroll
  acknowledgement. No-op final animation frames need no acknowledgement.
- JavaScript bridge calls explicitly return null, resolving unsupported-result
  errors in native diagnostics. The method/parameter table is shared rather than
  constructed on every call; real bridge failures remain logged.
- Removed the unused `ChatPreferences.censored` forwarding method; the canonical
  text-rule implementation and its callers remain. Anchor replacement now walks
  retained DOM siblings using the existing records map and desired-ID set,
  removing a redundant set and full-history arrays/slices.

## Audit boundaries

Reviewed application Swift/JavaScript, resources, networking, playback, settings,
chat lifecycle and build scripts. A single-reference symbol is not proof of dead
code: UIKit, notification, PiP, URLSession and player callbacks remain necessary.
The app icon and license notices are required resources. Provider schema support,
authenticated stream resolution, bounded asset recovery, cancellation, cache
validation and playback retries remain. No provider transport, ad-filter,
decoder, emote catalog, bitrate or settings behavior was intentionally changed.

No additional broad deletion was justified by the evidence. This is a source
audit, not proof that every possible runtime path is exercised.

## Measurements

An isolated Chromium benchmark extracted the actual before/after anchor-selection
blocks, with 5,000 DOM rows, six alternating warm samples and 1,000 selections
per sample. Three retained-neighbor cases produced equivalent selections.
Median selection time: **1.6249 → 0.0066 ms (99.6% lower)**. This is a rare anchor
replacement operation, not an application-wide FPS or CPU improvement.

Native paired measurements use baseline `0b76ffada051cfafd898f2f260a7e3ead8b5ad26`,
Xcode 16.4 and Mac Catalyst on the same macos-15 runner within each pair. Current
code runs first; image caches are cold between copies. CPU combines the app and
WebKit processes (100% = one core); summed RSS is not physical iPad RAM usage.
Early pairs varied substantially and did not establish a universal frame-rate
or CPU improvement. Large retained histories remain a bottleneck; shorter code
alone is not evidence of faster rendering.

Final pair ([run 40393422307](https://github.com/EscapeAltDelete/Streamstiny/actions/runs/40393422307)):

| Workload | FPS before → after | Combined CPU before → after | Median RSS before → after |
| --- | ---: | ---: | ---: |
| 1,000 animated messages, 100 arrivals/s | 58.12 → 54.72 | 114.35 → 120.38% | 417.50 → 396.11 MiB |
| 5,000 retained messages, following | 20.56 → 21.58 | 135.36 → 130.74% | 572.83 → 582.59 MiB |
| 5,000 retained messages, reading + 100 arrivals/s | 26.29 → 24.95 | 132.43 → 134.39% | 598.10 → 585.28 MiB |

Reading workload p95 model-update-to-DOM latency was **77 → 105 ms**;
500/500 arrivals were observed in both copies. Both wrote the renderer offset
zero times during interaction and once afterward. Hidden-chat combined CPU was
3.57 → 3.10%. Cold picker content readiness was 1,107 → 1,121 ms; warm readiness
570 → 614 ms. Cold visible-asset request count remained 40; the 35 warm requests
were all HTTP-cache hits in both copies. Picker behavior was not optimized here.

The preceding valid pair ([run 40393078792](https://github.com/EscapeAltDelete/Streamstiny/actions/runs/40393078792))
showed a larger slowdown: 5,000-row following 36.61 → 23.15 FPS, and reading
40.30 → 27.40 FPS. That version predates only the final no-op animation guard
and native test-input correction. These differences are not erased by the final
pair. The results **do not establish no overhead or a general CPU/FPS win**.
Stable following is a correctness requirement; traces of the original target
also show full-viewport overscroll between updates, so an end-of-phase distance
of zero alone does not establish equivalent intermediate painting. Its effect
on the timing differences was not isolated. No causal claim is made from that
observation. Further physical-device profiling of large-history layout and the
linear Swift reconciliation (~11–13 ms median at 5,000 rows) remains warranted.

Full phase summaries, including the slower results, are in
[the measurement JSON](chat-ux-2026-10-26.json). A diagnostic paired run
40392571361 passed all seven current-code tests but failed its baseline because
temporary tracing referenced variables absent from the old code; that pair is
excluded. Earlier scroll-test failures drove the acknowledgement fix and the
correction from DOM-only input to native scroll-view input. Assertions were not
relaxed to obtain passing runs.

## Verification

The browser suite covers state transitions, no repeated follow notifications,
bursts during animated jumps, delayed scroll acknowledgements, gesture
cancellation, Reduce Motion, retained-neighbor anchoring, pruning during touch,
background cleanup, picker/search, asset loading and animation regressions.
All 19 Python build-tooling tests pass.

Native tests use the actual coordinator, WKWebView and UIButton at portrait and
short landscape-like sizes. They assert visibility, minimum hit area, safe-area
placement, preservation of reading position, latest-message arrival during a
jump, resumed following and renderer-process recovery, retaining screenshots.
Waiting for DOM arrival and settled geometry avoids counting an asynchronous
scroll request as a completed scroll.

Physical iPad/iPhone testing, Instruments energy/GPU profiles and real finger
gestures are unavailable in this environment. Simulator/Catalyst checks cannot
establish physical-device memory, battery consumption or sustained 60 FPS.
